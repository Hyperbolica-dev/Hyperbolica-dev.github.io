# Optional LMTI submission Worker

Independent Cloudflare Worker using private KV, a native rate-limit binding and one SQLite Durable Object. Commands below run from `worker/`, except the test command. Use Node 22.13+ and Wrangler 4. Production Worker name `submit`, KV namespace ID, exact production CORS origin and existing secrets are preserved in `wrangler.toml`. Never create a replacement production KV namespace or delete its existing rows during this upgrade.

## Upgrade and one-time bootstrap

1. Authenticate with the existing production account (`npx wrangler@4 login`). Preserve the existing `STATS_TOKEN` and `RATE_SALT_SECRET` secrets; deployment does not replace them. For a **new isolated installation only**, create its own KV namespace, update its ID/name/origin, and set both secrets with `npx wrangler@4 secret put STATS_TOKEN` and `npx wrangler@4 secret put RATE_SALT_SECRET`. Use independent high-entropy secrets (at least 32 random bytes); never commit them or put them in frontend configuration.
2. Review `DAILY_SUBMISSION_LIMIT = "1000"`. This is a globally serialized UTC-day **admission** ceiling, not a Worker request quota. Failed/ambiguous writes consume a slot, deliberately. Existing submissions from today must be included in the bootstrap's `used` value. Set a lower limit if the account's other KV usage requires more headroom. The native binding allows six attempts per 60 seconds per daily HMAC IP identifier and scope; submit and counts have separate scopes. Native limits are approximate and local to Cloudflare locations, not a global guarantee.
3. Deploy the Worker before deploying the frontend: `npx wrangler@4 deploy`. The `v1-submission-ledger` migration creates SQLite class `SubmissionLedger`; the binding always addresses object name `global-v1`. Keep this migration and object name stable on subsequent deployments. Before bootstrap, both submissions and public counts return 503: this intentionally pauses ingestion while old records are counted. Private `/stats` remains available. Do not roll back to the old ingestion code while taking the snapshot.
4. Using the account owner's private KV administrative access, paginate **all** `submission:` keys and read their JSON once. Do this after deployment and after any old in-flight writes and KV propagation have settled; repeat the private snapshot if necessary until stable. Preserve every existing row, including GPT calibration records. Compute `human` from `row.mode === "human"`, `agent` from `row.mode === "agent"`, and `used` from rows whose `ts` is on today's UTC date. Do **not** derive these from `/stats`'s `who` counts: an agent can self-report `who: "human"`. Investigate missing/invalid modes instead of silently dropping records. The parent/operator may supply these verified counts; there is no public scan or automatic zero bootstrap.
5. Call **once**, using a private administrative client: `POST https://<worker-host>/admin/bootstrap`, header `Authorization: Bearer <STATS_TOKEN>`, body `{"human":H,"agent":A,"day":"YYYY-MM-DD","used":T}` (JSON, maximum 4096 bytes). Here H/A are the entire existing snapshot, T is that snapshot's submissions on the supplied current UTC day. Keep the secret in a hidden prompt or protected client configuration, not command arguments/history. No Origin is needed; if supplied it must match production exactly. This route accepts `application/json` as well as plain text. Expected response: 200 `{"ok":true}`. Missing/wrong secret: 401; invalid counts/date: 400; already initialized: 409. If the response is lost, a repeated request returns 409 instead of reseeding. The bootstrap transaction seeds historical totals and today's used budget atomically; it never changes KV. If midnight passes before the request, recalculate T/day. Never send placeholder zero counts for existing data.
6. Read `GET https://<worker-host>/counts` without credentials. Expect exactly `{"human":H,"agent":A}` before new accepted submissions. Set the frontend's existing `src/lib/lmti/config.ts` `SUBMIT_ENDPOINT` to the Worker root URL ending `/`; the UI appends `counts`. Do not use `/stats` as the public endpoint. Deploy the frontend with retry UUID support only after bootstrap succeeds.
7. Perform acceptance requests in a **separate development Worker/namespace**, not disposable production submissions: one human nickname submission, one agent submission, retry the same UUID, reach the per-IP rate limit, exercise a small daily ceiling, and check cached counts after 60 seconds. Check unauthorized bootstrap/stats and wrong-origin requests. In production, read-only count/CORS checks are sufficient unless the owner explicitly wants a real retained submission.

Future deployments retain the DO and **must not bootstrap again**. A missing/unavailable/uninitialized ledger fails closed, never resets counts to zero. If bootstrap totals were wrong, stop and perform an explicit owner-controlled data correction/migration; this public Worker intentionally has no counter-reset or arbitrary SQL endpoint. Deleting KV records does not decrement lifetime accepted totals. Deleting the DO or changing its name loses the budget, totals and retry receipts and requires an operator-controlled migration, not an ordinary redeploy.

## API

- `POST /`: exact `Origin: ALLOWED_ORIGIN` and `Content-Type: text/plain` (optional UTF-8 charset). Body capped at **4096 UTF-8 bytes**, including streaming/declared sizes. No-origin submissions are rejected. `OPTIONS /` allows only POST and Content-Type from that origin. CORS is not authentication; non-browser clients can forge Origin.
- Payload: `{v:3,code,mode,who,model,think,fb,hp:"",nickname?,durationMs?,submissionId?}`. Payloads without optional fields remain valid. Version 2 submissions are rejected; stored historical rows remain untouched and are not v3 calibration samples. `mode` is human/agent; `who` and `think` retain the existing allow-lists. `model` remains at most 40 Unicode code points after C0/C1 controls are removed. `fb` has at most 24 distinct `{q,text}` entries, q 1–24 and text at most 300 code points. Extra fields are discarded.
- Optional `language` is exactly `en` or `zh-CN`; other supplied values are rejected. It is stored privately with the submission and participates in idempotency. Missing historical language is not inferred or backfilled. Public counts never expose it; calibration must keep languages separate.
- For **human mode only**, optional `nickname` must be a string. Unicode control (`Cc`) and format (`Cf`) characters are stripped, surrounding whitespace is trimmed, and more than **32 Unicode code points after normalization** is rejected, not silently truncated. Empty normalized names are omitted. Agent nicknames are ignored regardless of content/type and never persisted. Nicknames are private voluntary free text, not verified identities or unique people.
- For **human mode only**, optional `durationMs` must be a finite nonnegative safe integer no greater than **604800000 ms (seven days)**; invalid values are rejected, never coerced. Agent durations are ignored regardless of content/type and never persisted, even if `who` says human. It is voluntary client-reported wall elapsed time from Start to Finish, including breaks/background time, not active time or trusted performance evidence. The frontend freezes it before showing results and sends it only after consent and Submit. Missing/legacy/debug durations remain absent; no historical records are backfilled. Client start/finish timestamps are discarded, and neither duration nor timestamps are returned by public counts.
- Positional codes use `LLMQ3p`, all 24 unique IDs, blank 0, exact bundled-bank option positions (including fractions, probe X, skip S, unknown U, and silent-sticker T), and existing canonical-number validation. Special tokens are accepted only where the bundled question offers them. No independent answer mapping is introduced. Deploy the matching frontend and Worker together after editorial approval.
- `submissionId` is an optional UUIDv4. The frontend generates one for each distinct payload/attempt and reuses it for retries. Repeating a completed ID and identical sanitized payload returns 200 without another write/count; changing a payload under the same ID returns 409 `conflict`. Compact receipts are retained with the ledger, so repeat requests do not consume additional daily slots. Legacy clients without an ID use a sanitized-payload digest: identical legacy payloads deliberately collapse to a single submission while the ledger is retained. New distinct attempts should always supply a new UUID.
- Success: 200 `{"ok":true}`, only after KV persistence and the atomic SQLite count/receipt commit. Errors return a generic `{"error":"..."}`: 400 `invalid`, 403 `origin`, 404 `not_found`, 405 `method`, 409 `conflict`, 429 `rate` or `capacity` (Retry-After 60), 503 `unavailable`. Daily capacity may remain exhausted until UTC midnight; Retry-After is a minimum retry interval, not a promise of renewed capacity.
- `GET /counts`: public, no secret, no body. Returns only `{human:number,agent:number}`: **accepted submissions, not unique people**, grouped by mode. Never returns nickname, code, feedback, model, identifiers, timestamps or raw rows. The response has a fixed two-field shape and bounded safe-integer values. Supplied wrong Origins are rejected, and exact-production CORS is rebuilt for each response. Successful snapshots are cached for approximately 60 seconds in isolate memory and Cloudflare Cache API; the canonical cache key discards query strings and Origin to prevent query-string cache busting. Concurrent isolate misses share a promise. Browser cache lifetime does not extend the snapshot's expiry. Errors are not cached; dependency failures return 503 rather than fabricated zeroes. Native limits also protect counts requests before storage. No counts request enumerates KV.
- Private compatibility endpoint `GET /stats?token=SECRET` is unchanged: authenticated with `STATS_TOKEN`, returns `{"counts":{"human":0,"claude":0,...}}` grouped by **who**, paginating only `submission:` keys. Missing/wrong secret returns 401. Non-browser requests need no Origin. This owner-only legacy scan is potentially expensive/eventually consistent and is **not** used by the UI or bootstrap counter. Responses use `Cache-Control: no-store`. Do not expose/bookmark its bearer-token URL or enable analytics/request logs around it.

## Consistency, overload protection and privacy

Native rate limiting happens **before body consumption, KV, or Durable Object storage access** on submission requests. Missing IP, rate binding, HMAC secret, KV, ledger or valid daily limit fails closed. The trusted Cloudflare `CF-Connecting-IP` is used transiently for `HMAC-SHA-256(RATE_SALT_SECRET, scope + newline + UTC-date + newline + IP)`. Only that daily identifier reaches the native limiter; neither raw IP nor this hash is stored in KV, the ledger or application logs. Shared IPs share a limit; IPv6/IP rotation and different Cloudflare locations can evade an approximate local rate limit. Rotating the secret/day rotates identifiers.

The single named DO serializes admission using SQLite, with no KV read/check/write counter race. It reserves a daily slot and a durable outbox receipt before writing the private KV row. A successful KV put is followed by one SQLite transaction incrementing the mode total and marking that receipt complete. Retries always write the **same** `submission:<id>` key, so a lost KV acknowledgement cannot create extra rows. If KV or the count commit fails, the response is 503 (not false success), the reserved slot remains consumed, and an alarm retries at most 20 pending rows per minute. A retry after a recovered commit returns success without counting again. A failed request can therefore be durably completed later; callers must retain their retry UUID instead of generating a new one after an error. Alarms and delayed recovery can update today's visible totals for slots reserved on an earlier UTC day; the daily ceiling bounds new admissions, not the completion time of previously admitted work.

No distributed transaction spans KV and SQLite: after an ambiguous write, KV may temporarily contain a row not yet reflected in public counts. Durable recovery closes that gap when dependencies recover. KV itself is eventually consistent, so private `/stats` may temporarily lag the ledger. External manual KV edits or deletion are not automatically reflected in lifetime totals. Permanent infrastructure loss needs owner recovery from private backups; no implementation can promise exactly-once recovery after deleting its ledger. Do not use old Worker code concurrently with this ledger for new writes.

KV submission values contain only `{ts,code,mode,who,model,think,fb,nickname?,durationMs?}`. `ts` is the existing private server receipt time, not a client start/finish timestamp. The retry ID is the key, not an extra row field. Old UUID rows remain untouched. Pending outbox rows temporarily contain that same private JSON; after completion only retry ID, payload digest, mode and creation time remain in SQLite. These compact receipts have no automatic expiry, to prevent replay from overwriting a prior KV row while double-counting it. Submission KV rows also have no automatic expiry. Review both stores when implementing retention/deletion policies; voluntary model/feedback/nickname text can identify a person. No raw-data endpoint or application logging is added. Wrangler observability stays disabled.

**This is not DDoS prevention and does not cap billable Worker requests.** Every incoming request can still invoke a Worker; native limits are approximate, public cache misses still cost work, and a sufficiently distributed source can exhaust the daily admission allowance or overload the single DO. A 1000/day limit protects normal new-ingestion/storage growth, not all KV operations: idempotent retries/recovery and owner-only scans can add operations. Provider request quotas, CPU/storage limits, billing alerts and any available account-level firewall/rate rules remain separate operational controls. Monitor provider usage privately and lower/disable ingestion if needed. This implementation makes no outbound third-party requests.

## Tests (parent integration step)

From the repository root, with Node 22.13+:

```sh
node --test worker/worker.test.mjs
```

Tests use Node's built-in runner, Web Crypto, SQLite (`node:sqlite`), an in-memory KV fake and fixed clocks. They cover existing CORS/body/validation/stats contracts plus Unicode nickname normalization, optional human duration boundaries/agent omission/private storage/retry identity, native pre-body limiting, missing dependencies, authenticated one-time bootstrap, existing-mode counts, public fixed shape/cache behavior, concurrent daily admission, retry conflicts/deduplication, ambiguous KV writes, alarm recovery and SQL rollback after KV success. SQLite is real in-memory SQL; Cloudflare rate limiting, Cache API, networking and Durable Object deployment/migrations still require an owner-run isolated runtime smoke. No tests, builds, linters, deployment or production writes were run by the implementation agent.
